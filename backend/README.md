# Sandbox Protocol backend

This is a free-tier-first Cloudflare Worker foundation. It is not deployed by CI and does not create Cloudflare resources automatically.

## Components

- **Workers**: HTTPS API and future server-side AI gateway.
- **R2**: Workshop asset and metadata storage.
- **Durable Objects**: ephemeral WebSocket room coordination (16 concurrent sockets per room in this initial implementation).
- **Supabase Auth (optional integration point)**: upload/delete endpoints verify Supabase HS256 access tokens using a server-only secret. No Supabase project is created or configured by this repository.

## Workshop API

Base URL: your deployed Worker URL.

| Method | Path | Purpose | Authentication |
|---|---|---|---|
| GET | `/health` | Health check | No |
| GET | `/api/workshop/items?limit=20&cursor=...` | List public item metadata | No |
| POST | `/api/workshop/items` | Upload an item as multipart form data | Supabase access token |
| GET | `/api/workshop/items/:uuid` | Read public item metadata | No |
| GET | `/api/workshop/items/:uuid/asset` | Download asset | No |
| DELETE | `/api/workshop/items/:uuid` | Delete own item | Supabase access token |
| WS | `/api/rooms/:roomId` | Ephemeral room chat/state relay | Supabase access token |

Upload form fields: `file` (required), `name` (required), `description`, `category`, and comma-separated `tags`.

Accepted assets: GLB, glTF JSON, OBJ, MTL, PNG, JPG/JPEG, WEBP and JSON. Maximum size is 25 MiB per file. Executables and arbitrary script files are not accepted. This is an initial allowlist, not a malware scanner or full asset sandbox; uploaded model files should still be parsed defensively by clients.

Metadata includes an opaque UUID, name, description, category, tags, owner ID, original filename, byte size, MIME type, R2 object key, creation timestamp and version.

## Configure and deploy manually

1. Create a Cloudflare account and install Node.js LTS.
2. From `backend/worker`, run `npm install`.
3. Create an R2 bucket named `sandbox-protocol-workshop` (or change `bucket_name` in `wrangler.toml`).
4. Create/configure a Supabase project if user accounts are needed. Configure its legacy HS256 JWT signing secret as a Worker secret named `SUPABASE_JWT_SECRET`. This implementation intentionally accepts only HS256 Supabase access tokens with `role=authenticated`. If the Supabase project uses asymmetric signing keys, replace the verifier with JWKS verification before enabling uploads.
5. Set `ALLOWED_ORIGINS` to the exact trusted origins where applicable. Packaged file:// clients may send a null origin; bearer-token validation remains mandatory for writes. Do not enable cookie authentication with wildcard CORS.
6. Run tests: `npm test`.
7. Run `npx wrangler login`, then `npx wrangler deploy`.

The first deployment creates the Durable Object class from the migration in `wrangler.toml`. Creating the R2 bucket and configuring Worker secrets are manual steps. Deployment is deliberately not part of GitHub Actions.

## Security and operational notes

- Never put Supabase signing secrets or cloud AI provider keys in the game client or Git.
- Upload/delete require a verified bearer token; users can delete only their own items.
- Public metadata and asset downloads are currently unauthenticated. Add moderation, reporting, malware scanning, quotas, rate limits and a review/publish state before opening Workshop broadly.
- R2 object keys are generated by the server; user filenames never become storage paths.
- The initial metadata index is a paginated R2 object listing. At larger scale, use a database index (Supabase/Postgres or D1) for search, ratings, categories and moderation.
- Durable Object rooms relay JSON `chat` and `state` messages up to 8 KiB, with a 16-socket cap. They are an ephemeral transport foundation, not a finished authoritative physics/multiplayer server.
- No AI provider is called by this Worker yet. The future AI gateway should use server-side provider secrets, per-provider timeouts, budgets, user quotas and an explicit fan-out policy. Local inference remains client-side and available offline.
- There is no billing, subscription, payment SDK or entitlement enforcement in this backend. Developer builds remain unrestricted.
